ملف تعليمات إلزامي لوكلاء التطوير العاملين على مشروع LibreChat

Target path: /mnt/ai/LibreChat/sh/README.md

1. القاعدة الحاكمة
بعد كل مرحلة من مراحل التطوير أو الإصلاح أو الدمج أو التهيئة، يجب إنشاء سكربت اختبار مستقل وقابل للتنفيذ داخل مجلد sh/ يغطي كل عنصر وكل مطلب وكل تكامل نُفِّذ خلال تلك المرحلة. لا يكفي تشغيل اختبارات موجودة أو الاكتفاء بوصف شفهي.

path: /mnt/ai/LibreChat/sh/هنا يتم وضع جميع الاختبارات

لا يُعلن اكتمال المرحلة ولا يبدأ المرحلة التالية إلا بعد:
1. تحديد نطاق المرحلة ومتطلبات قبولها وربط كل متطلب بحالة اختبار محددة.
2. إنشاء سكربت الاختبار الخاص بالمرحلة وفحص صياغته.
3. تشغيل الاختبارات الممكن تنفيذها آليًا وإظهار النتائج الفعلية دون ادعاءات.
4. تسليم المستخدم أمرًا واحدًا واضحًا ليشغّل السكربت بنفسه على السيرفر.
5. قراءة مخرجات تشغيل المستخدم، وتصحيح أي فشل، وإعادة تسليم الاختبار حتى يعتمد المستخدم المرحلة صراحةً.
وجود PASS في الاختبارات الآلية لا يحل محل اعتماد المستخدم.
2. موقع الملفات وقواعد التسمية
- مكان الاختبارات: /mnt/ai/LibreChat/sh/.
- اسم سكربت كل مرحلة: phase-NN-<short-name>-test.sh، مثل phase-01-auth-test.sh.
- التقارير الناتجة: sh/reports/phase-NN-<short-name>-<UTC-timestamp>.log، وملف JSON مرافق إن أمكن.
- ملف تعريف اختبارات المرحلة: sh/phase-NN-<short-name>-checks.md، يحتوي على المتطلبات وعناصر التحقق والأدلة المطلوبة.
- يُمنع استبدال اختبارات مراحل سابقة أو حذفها بلا طلب صريح.
- ممنوع إنشاء نسخ احتياطية من الكود أو ملفات التكوين القابلة لإعادة الإنشاء. التقارير التشغيلية ونتائج الاختبارات ليست نسخًا احتياطية.
3. محتويات سكربت الاختبار الإلزامية
يجب أن يكون كل سكربت Bash صالحًا للتشغيل على الخادم المعني وأن يتضمن:
1. #!/usr/bin/env bash مع set -Eeuo pipefail أو معالجة مكافئة موثقة.
2. تحديد جذر المستودع بصورة صحيحة دون افتراض مجلد العمل الحالي.
3. فحص توفر الأدوات والخدمات المطلوبة قبل استخدامها.
4. اختبارات مستقلة لكل متطلب وظيفي، وكل endpoint، وكل تكامل، وكل مسار فشل ذي صلة.
5. اختبارات حالات النجاح والأخطاء وحدود المدخلات والصلاحيات والعزل إن كانت ضمن نطاق المرحلة.
6. فحوص البناء وlint وtypecheck وunit/integration tests عندما تنطبق، مع عدم تشغيل أوامر تغيّر الإنتاج عشوائيًا.
7. فحص استجابة الخدمة الفعلية عبر HTTP أو CLI أو قاعدة البيانات، لا الاكتفاء بوجود ملف أو عملية.
8. PASS / FAIL / SKIP لكل حالة، مع سبب SKIP ودليل FAIL عند الإمكان.
9. ملخص إجمالي: عدد الحالات، الناجحة، الفاشلة، والمتجاوزة؛ وزمن التنفيذ.
10. إخراج سجل قابل للمراجعة من الطرفية وملف تقرير دون كشف أسرار أو رموز دخول.
11. رمز خروج 0 فقط عند تحقق شروط النجاح؛ رمز غير صفري عند أي فشل إلزامي، ولا تُخفَ الأخطاء باستخدام || true.
12. عدم مطالبة المستخدم بتجميع عشرات الأوامر؛ يجب أن يكفي أمر تشغيل واحد.
4. مصفوفة التغطية: لا عنصر دون اختبار
لكل عنصر تم تغييره أثناء المرحلة، سجّل في ملف checks.md:
ID	Requirement / Changed Component	Test Case	Expected Result	Actual Result	Status
T-001	مثال: endpoint جديد	طلب صالح	HTTP 200 وبنية صحيحة	يملأ بعد الاختبار	PASS/FAIL/SKIP
T-002	مثال: إدخال غير صالح	طلب ناقص	HTTP 4xx مناسب	يملأ بعد الاختبار	PASS/FAIL/SKIP


يجب ألا تبقى أي متطلبات أو ملفات مؤثرة بلا تغطية اختبارية. إذا تعذر اختبار عنصر آليًا، وضّح السبب وقدم خطوات تحقق يدوية دقيقة، ولا تعتبره PASS.
5. بروتوكول التنفيذ في كل مرحلة
قبل التنفيذ
- اقرأ ملفات الكود الفعلية وحدّد أسماءها والمسارات والأسطر ذات الصلة؛ لا تختلق بنية للمشروع.
- حدد معيار قبول قابلًا للقياس لكل تغيير.
- ميّز بين بيئات التطوير والاختبار والإنتاج.
بعد الانتهاء من البرمجة
1. أنشئ ملف sh/phase-NN-<short-name>-checks.md بمصفوفة التغطية.
2. أنشئ ملف sh/phase-NN-<short-name>-test.sh واستخدم أسماء الأوامر والمسارات الموجودة بالفعل.
3. نفّذ bash -n على السكربت ثم اختبارات البناء والأجزاء الممكن فحصها في البيئة الحالية.
4. شغّل السكربت، واحفظ الأدلة والنتيجة، وأصلح الإخفاقات الناتجة عن الكود.
5. قدّم للمستخدم أمر التنفيذ النهائي كما يلي:
cd /mnt/ai/LibreChat && bash sh/phase-NN-<short-name>-test.sh
6. اطلب نتائج تنفيذ المستخدم، وقارنها بمعايير القبول، ولا تنتقل قبل اعتماده.
تسليم المرحلة للمستخدم
يجب أن يتضمن ملخص التسليم:
- اسم المرحلة ونطاقها والملفات المعدّلة فعلًا.
- السكربت الذي أُنشئ، مع المسار الكامل.
- عدد حالات الاختبار، ونتائج PASS / FAIL / SKIP الفعلية.
- المتطلبات التي لم تُختبر وما يلزم للتحقق منها.
- أمر التشغيل الواحد للعميل.
- الحالة النهائية: AWAITING_USER_VERIFICATION أو BLOCKED أو APPROVED بعد موافقة المستخدم فقط.
6. ضمانات السلامة التشغيلية
- وضع الاختبارات الافتراضي قراءة وفحص فقط (Read-only)، ولا يجوز حذف بيانات أو إسقاط جداول أو تغيير خدمات الإنتاج أو إرسال رسائل حقيقية أو إنشاء طلبات فعلية دون موافقة صريحة وإعلان واضح.
- الاختبارات التي تحتاج إلى تغيير بيانات تستخدم بيئة اختبار أو بيانات معزولة؛ ويجب توضيح آثارها وإجراءات تنظيفها.
- لا تطبع المفاتيح أو كلمات المرور أو محتوى ملفات .env أو التوكنات في السجلات.
- استخدم timeouts للاتصالات الخارجية، وافحص رموز HTTP ومحتويات الاستجابة.
- لا تعتبر الخدمة صحيحة لمجرد أن المنفذ مفتوح؛ اختبر السلوك المتوقع.
- لا تترك إخفاقات SKIP أو أدوات ناقصة وتصف المرحلة بأنها مكتملة تمامًا.
- لا تنفّذ git reset --hard أو تغييرات مدمرة لإصلاح الاختبارات.
7. معايير قبول نهائية
المرحلة غير مكتملة إذا تحقق أي مما يلي:
- غياب سكربت المرحلة أو وجود اختبار شكلي دون تغطية.
- أي فشل مطلوب لم يُصلح.
- عدم تسليم أمر تشغيل واحد صالح على السيرفر.
- نتائج مزعومة بلا تشغيل فعلي أو أدلة.
- أي عنصر جديد بلا حالة اختبار أو استثناء موثق.
- غياب موافقة المستخدم على نتائج الاختبار.
القاعدة النهائية: اكتب الكود، اختبر كل عنصر، سلّم اختبارًا قابلاً لإعادة التشغيل، ثم انتظر اعتماد المستخدم قبل أي مرحلة جديدة.
