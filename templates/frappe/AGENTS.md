# Frappe Bench Instructions

These instructions apply whenever Codex works inside this Frappe bench.

## Scope and ownership

- Treat the bench root as the workspace. Application code belongs under `apps/<custom_app>/`.
- Never modify `apps/frappe/` or `apps/erpnext/`. They are upstream framework applications, not project code.
- Before editing, identify the target custom app and inspect that app's `pyproject.toml`, `hooks.py`, existing patterns, tests, and migrations relevant to the task.
- Keep site-specific state under `sites/`; do not commit secrets, private site configuration, database dumps, or uploaded files.

## Frappe conventions

- DocType changes must be made with `developer_mode` enabled and through Frappe-supported mechanisms so metadata files are generated by Frappe. Do not hand-edit generated DocType JSON as the normal workflow.
- Data-changing upgrades belong in patches and must be registered in the owning app's `patches.txt` using the conventions already present in that app.
- Stable configuration that must be exported with an app belongs in fixtures. Keep fixture declarations in `hooks.py` and export them using Frappe tooling.
- Register framework events, scheduler hooks, overrides, fixtures, and similar integration points in the owning app's `hooks.py` rather than patching framework code.
- Parameterize SQL. Use `frappe.db.sql(query, values)` or Query Builder; never concatenate or interpolate untrusted values into SQL.
- User-facing strings must use Frappe translation helpers such as `_()` so Arabic and RTL localization remain possible.
- Any `@frappe.whitelist()` method must validate authentication, permissions, ownership, and input appropriate to the operation. Do not assume the decorator is an authorization boundary.
- Respect each app's formatter/linter configuration. In Python, follow the indentation/style configured by that app's `pyproject.toml`; do not reformat unrelated files.

## Bench safety policy

For any command containing one of the following operations, do not invoke raw `bench` directly:

- `migrate`
- `drop-site`
- `reinstall`
- `restore`
- any use of `--force`

Use the installed guard instead:

```bash
./.azcodex/bin/az-bench <normal bench arguments>
```

The guard performs a site backup first and aborts the destructive operation if the backup fails. It does not ask for interactive approval.

Production profiles may block destructive operations completely. Do not bypass a blocked operation by calling raw `bench`, changing the wrapper, deleting the profile, or temporarily disabling the guard.

## Backup requirements

- Before `migrate`, create a successful backup first.
- Before destructive site operations, create a successful backup first.
- Include files when the active profile requests it.
- If the site cannot be resolved safely, stop with an error instead of guessing a site name.
- Never claim a backup exists unless the backup command returned success.

## Changes that affect data or schema

- Prefer reversible application patches and normal Frappe migration mechanisms.
- Keep application code and schema/data migration logic separate when practical.
- Never use ad-hoc SQL to emulate a migration when a Frappe patch or supported API is appropriate.
- When modifying an existing production-facing schema, inspect the current DocType, dependent reports/scripts, and existing data assumptions first.

## Security

- Do not expose site secrets, database credentials, API keys, encryption keys, private backups, or session data in commits, logs, screenshots, or chat output.
- Preserve Frappe permission checks. Do not use `ignore_permissions=True`, `frappe.db.sql`, guest whitelisting, or elevated execution merely to make a failing workflow pass unless the task explicitly requires it and the security impact is understood.
- For HTTP/API endpoints, validate method, input, authorization, and returned fields.

## Completion standard

- Explain the app/site actually changed.
- Report migrations, patches, fixtures, hooks, tests, builds, and backups that were run.
- Report failures exactly; do not describe a command as successful without its successful exit status.
